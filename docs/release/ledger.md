# Desktop release ledger

The release workflow's only mutable central state is `desktop/stable/state.json` on the repository's `gh-pages` branch. `desktop/stable/latest.json` is generated from that ledger in the same branch commit. `desktop/release/ledger.mjs` owns deterministic transitions; `desktop/release/pages-state.mjs` serializes state and derives the updater feed from one validated snapshot. The checked-in writer does not create a second release record.

## State shape

The schema version 1 ledger contains:

- `revision`: monotonically increases for each accepted state transition and protects publishers from stale reads.
- `last_reconciled_main`: current `main` head SHA included in the last reconciliation.
- `current_minor`: manually selected `major.minor` series; PR labels do not change it.
- `minor_changes`: actor, reason, and timestamp for each authorized milestone change.
- `reserved_versions`: immutable version/tag reservations, including preexisting tag gaps and failed unpublished reservations.
- `processed_merges`: one record per approved main merge, with exact source SHA, PR, first-parent order, gate result, and reservation if Gate A passed.
- `recovery_events`: an additive audit record for an owner-approved recovery PR that restores the exact Git tree immediately before an unapproved merge; every merge held in that interval is recorded and remains unreleased.
- `releases`: platform delivery state for each gate-passing reservation.

Each release records the constitutional minimum fields: `version`, `tag`, `main_sha`, `pr`, `gate`, `macos`, `linux_asset`, `aur`, `blocked`, `reason`, and `created_at`. Platform objects use `pending`, `passed`, `failed`, or `superseded` and retain immutable artifact metadata when available. A release becomes public when its first validated macOS or Linux asset is distributed.

`.github/workflows/desktop-release.yml` invokes reconciliation after `main` CI completes, hourly at minute 17 UTC, and on owner dispatch. GitHub runs scheduled workflows only from the default branch and may delay or drop them under load. The workflow uses the maximum Actions concurrency queue; the reconciler still sorts full first-parent history and does not rely on event order. It requires the repository owner's approval of the merged PR's final head before merge and checks every required job from the `ci.yml` push run for that exact merge SHA. Missing PR records or pending Gate A results stop the watermark. An unapproved merge also stops reconciliation; descendants are held until an owner-approved PR restores the exact pre-hold Git tree. The ledger records that recovery checkpoint and the held PRs, which do not receive releases. Before any trusted tooling SHA exists, a dedicated failure-only recorder may append one exact, owner-approved failed Gate A record; it does not reserve versions, create candidates, or advance the main watermark. Minor milestones use this workflow on `main`. Emergency block/unblock uses the separate `.github/workflows/desktop-release-controls.yml` on `main`, requires the repository owner and a reason, and uses the same Pages compare-and-swap writer. It shares a workflow-level Actions concurrency group with all release publishers and note writers, so the complete control run is serialized with publication. See [release operations](operations.md).

## Transition rules

- Reconciliation consumes approved, merged PRs in `git rev-list --first-parent --reverse` order. Duplicate merge events are no-ops. A failed Gate A merge is recorded without a version; repair requires a new approved PR. A discovered unapproved merge stops all descendants; only a later owner-approved merge whose Git tree equals the exact tree before the held interval can recover it. The interval is durably recorded in `recovery_events` and receives no releases.
- The first unused version is `0.1.0`. A passing merge reserves the next patch in the explicitly selected minor series. Reservations are never reassigned, so a failed unpublished reservation can leave a gap.
- Platform publication checks the ledger revision, source SHA, version, immutable GitHub asset URL, and checksum. macOS publication also requires both DMG/updater archive metadata and a signature already verified by the publishing job. A retry may reuse only the same recorded artifact metadata.
- A newer platform publication supersedes older pending/failed delivery for that platform. A lower version cannot publish after a higher version is already passed.
- AUR publication requires the public release's validated Linux asset and a PKGBUILD/.SRCINFO checksum tied to that exact archive. AUR publication status is separate from Linux asset status.
- Emergency block/unblock records actor and reason. A block prevents new platform writes and removes that version from the derived macOS feed. It does not remove already published GitHub/AUR artifacts. Release publishers, emergency controls, and note writers share one workflow-level concurrency group. A block becomes effective when its serialized control run commits the ledger; GitHub does not promise queue order, so an earlier queued publisher may run first. Publishers that start after the block commit reread the ledger and reject the blocked version. The release notes explain the AUR recall limit.
- `latest.json` is a projection of the newest unblocked macOS release with a passed signature-verified ARM64 updater archive. Linux and AUR states never enter the Tauri updater feed.

`desktop/release/pages-publisher.mjs` fetches `gh-pages`, regenerates both files, and commits them together. A rejected push is classified by rereading the branch: when the remote advanced, the publisher resets to that state and reruns reconciliation before retrying; when it did not advance, publication fails with a branch-rule/credential error. It never force-pushes. Each git push uses a short-lived, repository-scoped GitHub App token supplied as `ELEF_RELEASE_STATE_PUSH_TOKEN`; Pages checkouts do not persist the general Actions token. Before release distribution and each ledger write, the scripts list applicable repository and inherited rulesets, fetch the full matching rule record, and validate the exact update-only rule and sole App bypass actor. The dedicated update-only ruleset is separate from deletion/non-fast-forward protection. The App, protected environment secrets, and remote ruleset must be configured before the first writer run; see [release operations](operations.md) and [STATUS.md](STATUS.md).
