topic: Markdown slide layouts proof of concept
updated: 2026-08-18T20:31

- (direction) Create a focused proof of concept for per-slide layouts rather than a broad PowerPoint-style catalog.
- (decision) Use a slide-start :::slide-layout{intro} directive; metadata remains in Markdown source, is hidden from rendered slides, and scopes to the next --- separator.
- (decision) Omitted layout metadata means slide-layout{body}; the proof of concept supports body and intro layouts.
- (capability) CAP-1: Authors can select an intro or body layout per slide in Markdown while preserving Markdown as the source of truth; success: parsing and round-trip visual editing preserve the directive and rendered output hides it.
- (capability) CAP-2: Intro slides present all slide content in a vertically centered, left-aligned block with a generous inset and substantially larger title; success: a rendered intro fixture visibly differs from body layout in the specified ways.
- (constraint) The existing standalone --- separator remains the canonical slide boundary; layout parsing must not reinterpret separators inside initial front matter or fenced code.
- (constraint) Visual editing must preserve slide-layout metadata when serializing source changes.
- (non-goal) Do not implement a large catalog of slide types, arbitrary per-slide style knobs, or a full theme/layout authoring system in this proof of concept.
- (event) Self-validation coherence pass: SPEC satisfies capability intent/success, design constraints, explicit non-goals, concrete success signal, stable capability IDs, and lean kernel structure.
- (event) Self-validation preservation pass: all confirmed decisions and load-bearing implementation details are represented in SPEC.md or implementation-plan.md; no unresolved blocking questions remain.
