topic: Replace the Elef root app with a Rails monolith
goal: Migrate Elef to a complete Rails product with a simple source-first authoring workflow and fast browser system tests
updated: 2026-09-02T20:12
---

- (direction by user) Replace the root Vite/Tauri app with a conventional Rails application on feat/make-rails-default; Tauri remains recoverable in Git history but is not a runtime in this branch.
- (decision by user) Rails owns the complete product: domain behavior, persistence, routing, rendering, editor workflow, and presentation mode.
- (decision by user) Use a Rails monolith with Rails views and Hotwire/Stimulus by default; introduce React only for a measured interaction problem and document why.
- (decision by user) The first product is single-user with database-backed presentations and a minimal presentation library.
- (decision by user) Store raw Markdown as the canonical presentation source; derive slides and rendered output rather than persisting slide geometry or a second authoritative representation.
- (decision by user) Target strict parity with the current Markdown and rendering behavior, including current supported syntax and edge cases.
- (decision by user) The first editor is source-first: users edit Markdown, then explicit Save persists it and updates the rendered slide preview.
- (decision by user) Do not use autosave in the first Rails product; preserve dirty state and warn before losing unsaved edits.
- (decision by user) Include a clean in-browser presentation mode with keyboard navigation; defer export.
- (decision by user) Use Rails unit and request tests plus Selenium-backed Rails system tests with headless Chrome for full browser workflows.
- (constraint by user) Do not add a semantic component DSL, filesystem projects, export/import, Tauri runtime, Python execution, AI features, or freeform canvas in this migration scope.
- (capability by user) A single user can create, list, open, edit, explicitly save, and reopen Markdown presentations stored in the database.
- (capability by user) A user can see a rendered slide preview derived from saved Markdown and enter a clean browser presentation mode.
- (capability by user) The product preserves current Markdown parsing and rendering behavior while making create/edit/save/reopen flows testable through Rails system tests.
- (assumption) The existing implementation and approved implementation specs are the behavioral reference for strict parity.
- (question) Which exact Rails Markdown rendering libraries and Rails version should be selected during architecture/scaffolding?
